# BACKEND.md — Бэкенд: состояние VPN, стек, модульность

> Продукт: ТГ-бот продаёт OpenVPN-конфигурации. PWA (iOS + Android) отдаёт конфиг и включает VPN. **Бэкенд — ядро системы**: генерирует конфиги, отдаёт их PWA, знает состояние VPN, ведёт базу клиентов. **n8n — уже готовый внешний сервис**, к которому наш бэкенд обращается как к API по требованию (не входит в ядро).

## 2. Считывание состояния VPN

### 2.1. Главный вывод (подтверждён исследованиями)

**Из чистого браузера/PWA определить статус VPN нельзя** — ни на iOS, ни на Android нет API для веб-контекста («Not possible to detect VPN in browsers»).

**Единственный кросс-платформенный способ — сравнение IP через бэкенд:**

```
PWA (клик «Проверить») ──fetch /api/vpn/status──► Бэкенд
   Бэкенд: видит реальный IP клиента (из соединения / XFF с trusted_proxies)
   Сверка: IP клиента == IP VPN-сервера?
     ── если да  ──► «VPN ВКЛЮЧЁН»
     ── если нет ──► «VPN ВЫКЛЮЧЕН»
```

**Почему надёжно:** это частный случай «VPN Exit Node Enumeration» — единственный метод детекции без ложных срабатываний по построению. Если трафик выходит через наш сервер — мы физически в VPN. Без внешних API, дёшево.

### 2.2. Три сигнала состояния

| Что узнаём | Способ | Источник |
|---|---|---|
| **«VPN включён?»** | IP клиента == IP VPN-сервера (через бэкенд) | IP-сравнение, надёжно |
| **«Чей конфиг активен?»** | Сервер: status-файл OpenVPN, **по Common Name** (CN → конфиг → покупатель в БД) | OpenVPN status / management |
| **«Есть ли активные сессии?»** | status-файл `--status 5` / management `status 3` (машинный формат) | OpenVPN docs |

**Идентификация по Common Name, а не по IP**: CN уникален (CN = сертификат = конфиг = покупатель), IP меняется. Несколько клиентов на одном сервере делят exit-IP — по IP «чей конфиг» не определить.

### 2.3. Пограничные случаи (учесть обязательно)

| Риск | Как учесть |
|---|---|
| **IPv6-утечка** (главный) | Проверять v4 И v6; `push "redirect-gateway ipv6"` или блокировать IPv6 |
| **Split tunneling** | Запрос статуса должен идти через туннель (весь трафик в конфиге) |
| **CDN/XFF-спуфинг** | Доверять только «правый не-свой» IP / `CF-Connecting-IP`; настроить trusted_proxies |
| **WebRTC-утечка** | Реальный IP может утечь через STUN — для статуса использовать только fetch на бэкенд |
| **Двойной VPN (РФ)** | Если клиент ставит свой VPN поверх нашего — честно показывать «не подтверждён» |
| **Несколько клиентов на сервере** | «Включён ли VPN» по IP работает; «чей конфиг» — только через CN |

### 2.4. Почему аппаратные пути не годятся для MVP

- **iOS**: нет системного «Get VPN Status» в Shortcuts (есть только у конкретных VPN-приложений, напр. Proton). Возврат через x-callback-url возможен, но тяжёлый и требует стороннего экшена.
- **Android**: `TRANSPORT_VPN` (ConnectivityManager) работает только в нативном коде (Capacitor-плагин `capacitor-vpn-detector`), не из браузера. Tasker «VPN Connected» — платный и сложный.

## 4. Модульность бэкенда

```
/backend
  /src
    /api            # REST-эндпоинты (Express/Fastify) + auth
    /services       # бизнес-логика: orders, configs, vpn-status, billing
    /openvpn        # коннектор к серверу: чтение status-файла, management, easyrsa
    /telegram       # bot: webhook/long polling, обработка команд, платежи
    /queues         # BullMQ: worker'ы (генерация конфига, проверка срока, рассылки)
    /n8n            # HTTP-клиент к внешнему n8n (по требованию)
    /workers        # фоновые задачи: парсер статуса, продление/отзыв, уведомления
    /config, /logger, /db, /metrics
```

### Ключевая связка «состояние VPN → БД → PWA»

```
OpenVPN server
  │ --status /var/run/openvpn-status.log 5   (или management 127.0.0.1:7505)
  ▼
[Worker: status-parser] (BullMQ, раз в N сек)
  │  парсит CN → активные сессии
  ▼
PostgreSQL: таблица sessions (cn, user_id, real_ip, connected_at, bytes)
  ▲
[API /api/vpn/status]
  │  берёт IP клиента из соединения → сверяет с IP сервера
  ▼
PWA: показывает статус (включён/выключен/чей конфиг/не подтверждён)
```

## 5. Логирование, очереди, наблюдаемость

- **Логи**: pino 10 (структурированные, JSON). Уровни: `req`/`res` для API, `job` для воркеров, `vpn` для парсера статуса.
- **Очереди**: BullMQ 6 на Redis 8. Типичные job'ы:
  - `config.generate` — генерация `.ovpn`/`.mobileconfig` (retry, отложенная)
  - `cert.revoke` — отзыв по истечении подписки
  - `status.poll` — периодический парсер status-файла
  - `notify.expiry` — уведомления «подписка заканчивается»
- **Метрики/трассировка**: OpenTelemetry (GA) + BullMQ OTel-интеграция; pino — для логов.
- **Обработка ошибок**: retry с экспоненциальным backoff в BullMQ, алерты по уровню ошибок.

## 6. n8n как внешний API (по требованию)

- n8n — **уже готовый, отдельный self-hosted сервис** (Docker, версия 2.29+).
- Наш бэкенд **не зависит** от n8n: продукт работает без него.
- Когда нужна готовая автоматизация (рассылки, интеграции с внешними сервисами, бизнес-процессы без кода) — бэкенд вызывает n8n через его **webhook/API** (`/api/v1/workflows/...`, execution API).
- Правило: **PWA никогда не ходит в n8n напрямую** — только через наш бэкенд. Единая точка входа и единый контроль доступа.
