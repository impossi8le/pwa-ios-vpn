# PRODUCT.md — Форма продукта: PWA (лендинг + кабинет) + нативные приложения

> **Решение (пивот)**: продукт больше не «PWA как единственный клиент». Теперь PWA — это **публичный лендинг + личный кабинет**, а VPN-управление в PWA остаётся только для **iOS и macOS**. Для **Android** VPN-управление живёт в **нативном приложении** (WebView кабинета + нативный OpenVPN-модуль). Windows/Linux — позже (на MVP — только кабинет в PWA + `.ovpn` вручную). Этот документ — эталон формы продукта; на него ссылаются остальные спецификации.

---

## 1. Общая картина

```
                          ┌───────────────────────────────────────────────┐
                          │                   PWA (сайт)                    │
                          │                                               │
                          │   /  (лендинг, публичный)                      │
                          │     · оффер, тарифы, FAQ                       │
                          │     · регистрация / вход (email+пароль)        │
                          │     · CTA: «Купить в боте», «Войти»,           │
                          │       «Скачать приложение» (Android)           │
                          │                                               │
                          │   /app  (кабинет, авторизованный)              │
                          │     · подписка, конфиги, оплата, статистика    │
                          │     · iOS/macOS → VPN-экран (установка/вкл/выкл)│
                          │     · Android/Win/Linux → кабинет без VPN-экрана│
                          └──────────────────┬────────────────────────────┘
                                             │
                    ┌────────────────────────┼─────────────────────────────┐
                    │                        │                             │
         ┌──────────▼──────────┐   ┌─────────▼─────────┐        ┌──────────▼───────────┐
         │  Нативное приложение │   │      Бэкенд       │        │      ТГ-бот           │
         │  (Android, MVP)      │   │  (ядро)           │        │  (продажа, оплата     │
         │  · WebView → /app    │   │  API, БД, очереди │        │  Stars, привязка)     │
         │  · OpenVPN-модуль    │──▶│  VPN-статус,      │◀───────│  привязка аккаунта    │
         │  · локальный статус  │   │  аналитика        │        │                       │
         └──────────────────────┘   └───────────────────┘        └───────────────────────┘
```

**Принципы:**
- **Бэкенд — ядро.** Все клиенты (PWA, нативное приложение, бот) ходят только в него. Единая точка входа.
- **PWA — публичная витрина + кабинет.** VPN-флоу внутри PWA — только для платформ, где браузер реально может управлять VPN (iOS/macOS).
- **Нативные приложения — Flutter-клиент.** Реализован [commuspaceVPN](https://github.com/impossi8le/commuspaceVPN): один код под Android/iOS (ics-openvpn / OpenVPNAdapter), desktop — stub. Кабинет (наш `/app`) — отдельный PWA; приложение и PWA связываются через общий бэкенд (auth + конфиги).

## 2. Правило роутинга в PWA («первый экран»)

VPN-экран открывается **первым**, только если выполнены ВСЕ условия:

```
(iOS | macOS)
  ∧ пользователь авторизован
  ∧ есть активная (непросроченная) подписка / конфиг
```

Иначе — домашняя страница кабинета (подписка, конфиги, оплата).

**Дополнительно:**
- **Детекция платформы** — по `navigator.userAgent` (`/iPhone|iPad|iPod/i`, `/Macintosh|Mac OS X/i`).
- **Ручной переключатель платформы** в настройках кабинета — на случай ошибки детекции (юзер на iPad с клавиатурой, десктоп-режим Safari и т.п.). Выбор сохраняется в `localStorage`.
- **Внутри нативного приложения** (`?embed=app` или app-токен): скрываем блоки «Скачать приложение», «Установить PWA», «Войти» — WebView уже авторизован приложением.
- macOS: VPN-экран открывается первым, но **тумблера Shortcuts нет** — показываем инструкцию (меню-бар / OpenVPN Connect) + кнопку «Проверить статус».

## 3. Платформы — матрица возможностей

| Платформа | PWA | VPN в PWA | Нативное приложение | Статус VPN |
|---|---|---|---|---|
| **iOS** | лендинг + кабинет | ✅ `.mobileconfig` + Shortcuts (Set VPN, iOS 16.4+) | ✅ **Flutter-клиент через TestFlight** (не App Store) | локальный (приложение) / IP-проверка |
| **macOS** | лендинг + кабинет | ⚠️ `.mobileconfig` + **меню-бар** (Shortcuts-тумблера нет) | Flutter desktop (stub VPN, вне сторов) | IP-проверка через бэкенд |
| **Android** | лендинг + кабинет | ❌ (из браузера нельзя) | ✅ **Flutter-клиент** (ics-openvpn) | **локальный** (VpnService) + репорт в бэкенд |
| **Windows** | лендинг + кабинет | ❌ | Flutter desktop (Windows runner, stub VPN) | IP-проверка через бэкенд |
| **Linux** | лендинг + кабинет | ❌ | Flutter desktop (stub VPN) | IP-проверка через бэкенд |

**iOS/macOS — не публикуем в App Store.** Пользователь указал, что на iOS/macOS стора не будет. iOS-сборка распространяется через **TestFlight** (добавление тестировщиков по Apple ID), macOS — вне сторов (DMG). Плюс остаётся PWA-VPN-флоу (`.mobileconfig` + Shortcuts для iOS, меню-бар для macOS). Подробно — [NATIVE-APPS.md](NATIVE-APPS.md) §3.

**macOS-нюанс (подтверждён):** установка через `.mobileconfig` — та же механика, что на iOS (`com.apple.vpn.managed` + `VPNSubType`; Apple-документация NETunnelProviderManager подтверждает создание конфигов через профили на macOS). Но **экшен «Set VPN» в Shortcuts есть только на iOS/iPadOS** — на macOS Shortcut лишь открывает панель Network. Поэтому на macOS VPN включается через меню-бар / OpenVPN Connect, а не через `shortcuts://`.

**Нативное приложение реализовано** — это Flutter-клиент [commuspaceVPN](https://github.com/impossi8le/commuspaceVPN) (`openvpn_flutter` v1.3.4, ics-openvpn на Android, OpenVPNAdapter на iOS, stub на desktop). См. [NATIVE-APPS.md](NATIVE-APPS.md).

## 4. Аккаунты и авторизация

- **Полноценный аккаунт на сайте**: email + пароль. Поле «телефон» зарезервировано под будущее (2FA, поддержка). Регистрация с лендинга и из кабинета.
- **Привязка к Telegram**: у Telegram-пользователя есть только никнейм (и не у всех — email). Схема привязки:
  ```
  Бот (/link или /start?link=...) → генерирует код привязки → юзер вводит его в кабинете
  ИЛИ юзер авторизуется в PWA через Telegram Login Widget → аккаунт создаётся/привязывается по tg_id
  ```
- **Что общего**: один `User` в БД может иметь `email + tgId`. Заказы и конфиги привязаны к `User`, независимо от канала.
- **Авторизация PWA**: JWT (короткий access + refresh). Telegram Login Widget (HMAC) — отдельный вход, связывающий аккаунт с tg_id.
- **Авторизация нативного приложения**: **app-токен** (долгоживущий, выдаётся после привязки аккаунта к приложению; отзыв через кабинет). Приложение держит его в KeyStore и шлёт в заголовке к API; WebView авторизуется по этому токену.

## 5. Оплата (два канала сразу)

| Канал | Где | Механика | `payment_method` |
|---|---|---|---|
| **Telegram Stars** | бот | `/buy → /pay` → Stars | `stars` |
| **Веб-оплата** | кабинет PWA | CryptoBot / ЮKassa (по решению) | `crypto` / `fiat` |

- Пользователь, пришедший с лендинга: может либо **перейти в бота** (`t.me/bot?start=pay_<plan>`), либо **оплатить в кабинете** (веб-оплата).
- Всё сводится к одному `Order` в БД: `status: created → paid → failed/refunded`.
